## Problem Statement

GPU를 빌려 쓰는 AI 스타트업의 연구·평가 에이전트는 이미 API로 GPU를 직접 띄운다(RunPod 공식 MCP, io.net Agent Cloud). 그런데 에이전트 단위로 "얼마까지, 어느 벤더에, 언제까지"를 강제하거나, 나중에 그 허락을 검증할 방법은 없다. 결제 레일은 누가 누구에게 냈는지만 기록하고, 누가 어떤 조건으로 허락했는지는 기록하지 않는다.

CFO Agent는 이 지출을 **작업 단위로 충전하고 감독하는 에스크로 금고**다. 금고는 Base Sepolia 컨트랙트로 구현한다. 허용 벤더, 수수료 포함 예산, 호출당 상한, 기한, STOP은 체인이 강제한다.

USER(PO, 창업자, 감사인 등)는 기록과 체인만 보고 세 가지를 다시 판정할 수 있다.
1. 각 지출이 **결정적 규칙**을 지켰는지: 벤더, 예산, 상한, 기한, STOP, 허용 GPU. 기록에 남은 입력값과 체인 상태로 게이트 규칙을 다시 계산한다.
2. 모든 hold와 충전 앞에 게이트 통과와 CFO 비거절 기록이 있는지.
3. 기록이 변조되지 않았는지.

범위 밖인 것도 있다. **정산 금액이 실제 GPU 사용량과 같은지**, 그리고 **Qwen 판단 기록이 실제로 Kiln이 낸 응답인지**(백엔드가 스스로 증명하는 값)는 검증하지 못한다. 한계 절을 참고한다.

해커톤 제출용이다. GWDC 2026 Korea, FuriosaAI × Bricksum Agent Finance 트랙, 권장 과제는 Challenge B다.

## What Makes This Cool

- **돈이 나가는 도중에 충전을 심사한다(헤드라인).** 결제 한 건을 막는 게 아니다. 작업이 진행되는 동안 잔액이 줄면 작업 에이전트가 충전을 요청하고, CFO Qwen이 목적에 맞는지 심사한다. 규칙은 통과했지만 목적을 벗어난 충전은 Qwen이 거절한다.
- **Akash mainnet의 결제 규칙을 EVM으로 옮겼다.** 대응 관계는 다음과 같다.
  - `fund` → AccountDeposit(예치)
  - `open` → CreateLease
  - `topUp` → AccountDeposit(충전)
  - `settle` → WithdrawLease
  - `close` → CloseLease
  - `refund` → CloseDeployment 시 남은 예치금 환불
- **벤더 가격이 실제 시장 가격이다.** Akash Console API `/v1/gpu-prices?debug=true`를 인증 없이 호출해 제공자별 대표 입찰가를 받는다. 최근 31일 온체인 bid를 GPU 1개당 시간당 USD로 환산한 값이다. 이 가격을 H100 제공자 세 곳에 붙여 벤더 A/B/C로 쓴다(예: $2.04 / $2.56 / $3.16). 벤더 자체와 실행은 mock이다.
- **추론비도 같은 금고에서 정산한다.** Kiln 추론비(`usage.cost`)를 작업 종료 때 같은 금고에서 INFERENCE 수취 주소로 정산하므로, 추론비도 온체인 예산 한도 안에 들어간다. 호출 1회는 약 $0.00014라서 절감 효과를 내세우는 기능은 아니다. 통제자도 같은 한도 안에서 감사받는다는 점을 보여주는 장치다.

## Premises

1. GPU 벤더는 mock이다. 가격만 Akash 실데이터이고, 실행은 시뮬레이션이다.
2. 숫자 신호(loss 정체, NaN, 예산, 기한, 용량, 허용 GPU)는 코드가 판단한다. CFO Qwen은 요청이 승인된 목적에 맞는지, 근거가 타당한지, 범위가 넓어지고 있지 않은지를 판단하고 사유를 작성한다.
3. 작업 하나에 GPU 벤더 하나. 벤더 이동은 체크포인트를 거쳐 대본대로 1회만 시연한다. mock 벤더들은 결제 방식이 같다.
4. 충전 hold는 금고에 실제로 잠긴다(`committed`). 체크포인트마다 벤더 실사용분을 정산 tx 1건으로 처리하고, 기록 해시를 체인에 고정한다.

## Approaches Considered

### Approach A: 시간 블록 — 채택 안 함
같은 금고를 쓰고 호출 주기만 1시간 단위로 바꾸는 방식이다. 시뮬레이션 시계는 A와 B 모두 필요하다. A를 버린 이유는 두 가지다. 변화가 없어도 블록마다 심사하느라 토큰을 쓰고, "블록이 끝나면 작업도 끊기나" 하는 개념적 혼란을 만든다.

### Approach B: 에스크로 금고 + 충전식 — **채택**
아래 Recommended Approach 참고.

### Approach C: 마일스톤 결제 — 채택 안 함
마일스톤마다 비용 추정이 필요하고, 시간 단위 과금으로 바꾸는 작업이 따로 든다.

### 제외한 결제 방식 (한 줄씩)
- **Akash 실제 사용:** 테스트넷에서 응답하는 GPU 제공자가 1곳뿐이고, Cosmos 스택이 추가로 필요하다(10\~16h). 가격만 가져온다.
- **x402 exact:** 수신자를 체인에서 제한할 수 없다. 벤더 1곳을 x402 `upto`로 정산하는 것은 stretch로 둔다. upto는 돈을 잠그지 않으므로 hold로 부르지 않는다.
- **Superfluid:** 잔액이 0이 되면 청산되면서 buffer를 잃는다.
- **approve / Spend Permissions / Safe allowance:** 수신자를 체인에서 제한할 수 없다.

## Recommended Approach

**Akash식 에스크로 금고(Base Sepolia, MockUSDC) + 충전식 주기 + Akash 실가격 벤더 A/B/C.**

### 등장 주체와 키
| 주체 | 정체 | 호출 가능 함수 |
|---|---|---|
| 창업자(ML 리드) | founder 지갑 | `fund`, `setVendor`, `setPaused`(STOP), `setMaxHold`, `refund`. **일시정지나 기한 이후에도** `settle`, `close` 가능 |
| 에이전트 백엔드 | agent 키(서버 hot key) | `open`, `topUp`, `settle`, `close`, `recordDecision` |
| 벤더 A/B/C | 팀이 만든 EVM 주소. 각각 Akash 제공자 1곳의 hostUri와 가격 스냅샷으로 라벨링 | 수취만 |
| INFERENCE | 팀의 Kiln 크레딧 상환 주소. 허용 목록에 포함 | 수취만 |
| feeTo | 마켓 수수료 수취 주소 | 수취만 |

- **agent 키만 탈취당하면:** 돈은 허용 벤더(와 feeTo 수수료)에게만 갈 수 있다. `maxHold`는 open/topUp **한 번의 net 금액**만 제한한다. hold를 여러 번 열고 settle로 한 번에 정산할 수 있으므로, 최악의 경우 금고의 **미지급 잔액 전체**(budget − Σpaid, 열린 hold 포함)가 허용 벤더에게 나갈 수 있다. 일시정지 중이거나 기한이 지났으면 그것도 안 된다. 그래서 STOP이 실질적인 방어선이다. (2026-09-29 검증 SEC-1로 정정)
- 허용 목록 밖으로 보내기, 예산 초과, `refund`, 허용 목록 변경은 불가능하다. 위반 시도는 모두 `Denied` 이벤트로 체인에 남는다.
- 게이트 키 co-signature(EIP-712)는 stretch로 둔다.

### 작업 명세 (목적의 출처, 창업자 서명)
- 창업자가 작업마다 명세 JSON을 쓴다. 필드는 `purpose`, `success_metric`, `allowed_gpu_types`, `job_cap_usd`, `deadline`이다.
- 창업자 지갑으로 서명한다(EIP-191). 서명과 명세 해시는 첫 기록에 들어간다.
- USER는 사후 검증으로 서명자가 금고의 `founder`인지 확인할 수 있다. 백엔드가 명세를 바꾸면 여기서 FAIL이 난다.
- Qwen은 심사할 때마다 명세 원문을 입력으로 받는다.

### 시뮬레이션 시계와 데모 규모
| 항목 | 값 |
|---|---|
| 시계 | 실제 1초 = 시뮬레이션 1분 (60배) |
| 예시 요금 | H100(B) $2.56/h → 실제 1초에 약 $0.043 |
| 초기 hold | 1 시뮬레이션 시간분. gross = $2.56 × 1.03 ≈ $2.64 |
| 충전 트리거 | 잔액이 현재 hold의 **40% 미만** (실제 약 36초 시점). 소진까지 약 24초가 남으므로 F1, 게이트, F2(재시도 포함 최대 약 20초), tx 확인이 그 안에 끝날 수 있다 |
| 늦은 승인 | 심사 중에 hold가 소진되면 실행기는 **AWAITING_TOPUP 상태로 대기**한다. 사용량은 쌓이지 않는다. 승인되면 이어서 진행하고, 거절되면 종료 절차로 간다 |
| 체크포인트 | 30 시뮬레이션 분(실제 30초)마다, 그리고 충전·중단·종료 때 |
| 기한 | 실제 블록 시간 기준. 요청한 시뮬레이션 시간은 60으로 나눠 실제 초로 바꾼다. 적용 기한 = min(명세 기한, 금고 기한) |

### 흐름
```
[준비] 창업자: fund(예산, 기한) · setVendor(A,B,C,INFERENCE) · setMaxHold · 명세 서명
[읽기] 모든 요청 직전 백엔드가 eth_call로 budget, committed, paused, deadline,
       vendorAllowed, maxHold, jobs[id]를 읽고, 값과 블록 번호를 기록에 넣는다
[추론 hold] 세션 시작: open(INFERENCE, 소액) → 추론비 전용 작업
[시작] 작업 에이전트(Qwen F1): 명세를 보고 벤더·GPU·초기 hold 제안
       → 게이트(규칙) → CFO Qwen(F2, 게이트 통과 시에만) → open(vendor, hold, recHash)
[진행] mock 실행기: 사용량 누적(60배), 30분마다 체크포인트 → settle(vendor 작업, 실사용)
       매 체크포인트에서 paused와 기한을 읽고, 해당하면 [STOP]/[기한]으로 간다
[충전] 트리거 = 잔액 < 현재 hold의 40%
       → F1: 진행 상황 + 근거 + 충전액으로 요청 → 게이트 → F2 → topUp(id, 금액, recHash)
[이상] NaN → 즉시 체크포인트 → settle → close. 코드가 처리하고 Qwen은 호출하지 않는다
       loss 정체(최근 3개 체크포인트 개선 < 0.5%) → 이후 충전 요청을 게이트가 LOSS_PLATEAU로 거절
[거절] 게이트나 Qwen이 거절 → recordDecision(id 또는 NO_JOB, code, recHash)
       → 남은 hold까지만 진행 → 소진되면 실행기 정지(HOLD_EXHAUSTED)
       → 체크포인트 → settle(실사용) → close(남은 hold 해제)
[이동] 트리거: A의 가용 수량 0, 또는 가격 급등
       → 체크포인트 → settle(A) → close(A) → 창업자가 setVendor(A,false)
       → 게이트 → Qwen → open(B) → 체크포인트에서 재개
[STOP] 창업자 setPaused(true, 사유해시) → 실행기는 다음 체크포인트에서 정지
       → 이후 에이전트의 open/topUp/settle은 Denied(PAUSED)
       → 창업자가 settle(정지 시점까지 실사용) → close → refund(미약정 잔액)
[기한] 기한에 닿으면 실행기 정지 → 에이전트 호출은 Denied(PAST_DEADLINE)
       → 창업자(대시보드 버튼)가 settle(실사용) → close → refund
[종료] 작업 close 때 F3로 영수증 설명 → 추론 작업 settle(INFERENCE 누적 추론비) → close
       → 사후 검증 PASS/FAIL
```
- **평가 순서:** 게이트가 먼저 판정하고, Qwen F2는 **게이트를 통과한 요청만** 판단한다. Qwen이 거절하면 그걸로 최종이다.
- 실행기는 hold 소진, STOP, 기한, NaN 가운데 하나라도 해당하면 멈춘다. 그래서 hold를 넘는 사용량은 생기지 않는다.
- **추론비 정산:** 수수료가 없다(INFERENCE 수취자는 fee 면제). 작업 개설 전이나 거절된 요청에서 쓴 추론비도 세션 시작 때 연 추론 작업의 hold에서 나간다.

### 코드 게이트 규칙
| 코드 | 규칙 | 입력 |
|---|---|---|
| `VENDOR_NOT_ALLOWED` | 벤더가 허용 목록에 없음 | 체인 `vendorAllowed`(읽기 단계) |
| `GPU_TYPE_NOT_ALLOWED` | 요청 GPU가 명세 `allowed_gpu_types`에 없음 | 서명된 명세 |
| `NO_CAPACITY` | 해당 GPU의 Akash 가용 수량이 0 | Akash 가격 캐시(스냅샷 해시를 기록) |
| `OVER_BUDGET_WITH_FEE` | committed + 금액×1.03 > budget | 체인 `budget`, `committed` |
| `OVER_MAX_HOLD` | 요청 금액이 `maxHold`를 넘음. open과 topUp 모두에 적용 | 체인 `maxHold`(데모 값 $6) |
| `OVER_JOB_CAP` | 작업 누적 gross가 명세 `job_cap_usd`를 넘음 | 장부, 명세 |
| `PAST_DEADLINE` | 현재 + 요청시간/60 > min(명세 기한, 금고 기한) | 체인 `deadline`, 명세 |
| `PAUSED` | STOP 상태 | 체인 `paused` |
| `LOSS_PLATEAU` | 최근 3개 체크포인트 개선이 0.5% 미만 | 실행기 로그 |
| `NAN_DETECTED` | loss가 NaN | 실행기 로그 |
| `QWEN_DENIED` / `QWEN_UNAVAILABLE` / `QWEN_UNPARSEABLE` | Qwen 거절 / 타임아웃·429 / 파싱 실패 | Kiln 응답 |

- **Qwen이 실패하면 거절한다(fail-closed).** 타임아웃은 20초다. 429·5xx나 파싱 실패는 1회 백오프 재시도한 뒤에도 실패하면 거절하고 기록한다.
- 체인이 강제하는 규칙(벤더, 예산, 상한, 기한, STOP)은 게이트와 컨트랙트가 **같은 코드 값**을 쓴다. 게이트에서 `VENDOR_NOT_ALLOWED`로 판정한 것은 컨트랙트에서도 `Denied(VENDOR_NOT_ALLOWED)`로 남는다.

### 컨트랙트: 거절 기록 방식 (Denied)
- **규칙 위반은 revert하지 않는다.** 돈을 움직이지 않고 `Denied(jobId, code, recHash)` 이벤트를 남긴 뒤 `false`를 반환한다.
  - 대상 위반: 벤더, 예산, `maxHold`, 기한, 일시정지, hold 초과 정산
  - 탈취 키의 시도까지 모든 멈춤이 체인에 남는다. 과제의 "멈춤은 조용하지 않고 기록되어야 한다"는 요구를 여기서 충족한다.
- **revert는 권한 없는 호출(`Unauthorized`)과 닫힌 작업(`JobClosed`)에만 쓴다.**
- 게이트나 Qwen이 tx를 보내기 전에 거절한 건은 `recordDecision(jobId 또는 NO_JOB, code, recHash)`로 같은 `Denied` 이벤트를 남긴다. `NO_JOB`은 `type(uint256).max`이고, 작업 개설 전 거절에 쓴다. 이때 요청 ID는 기록 파일 안에 있다.
- **일시정지·기한 이후 동작:**
  - 에이전트의 `open`/`topUp`/`settle` → `Denied`
  - 에이전트 `close`, `recordDecision` → 허용
  - 창업자의 `settle`/`close` → 항상 허용
  - `refund` → 미약정 잔액(`budget − committed`)만 돌려준다
- **수수료:** `feeBps = 300`(3%), 수취 주소는 feeTo, 정산 금액 기준이다. INFERENCE 수취자는 면제다. hold는 수수료를 포함한 gross로 예약한다. 불변식은 `committed(열린 hold + 지급된 gross) ≤ budget`이다.

| 항목 | 초안 상태 | 필요한 변경 |
|---|---|---|
| `fund`, `setVendor`, `setPaused(reasonHash)`, `refund(미약정 한도)` | 있음(동작 확인함) | 없음 |
| 창업자 `settle`이 일시정지·기한을 우회, `close`는 창업자·에이전트가 언제든 호출 | 있음 | 없음 |
| `settle`의 gross 기준 hold 초과 검사, 수수료 분배, 이벤트와 `recHash` | 있음(revert 방식) | 위반 시 revert → `Denied`로 변경 |
| `_agentChecks`, `_reserve`의 위반 처리 | revert | `Denied` 기록 후 `false` 반환으로 변경 |
| `Denied` 이벤트, `recordDecision`, `NO_JOB` | 없음 | **추가** |
| `maxHold` + `setMaxHold`(open과 topUp 모두 상한) | 없음 | **추가** |
| INFERENCE 수수료 면제(`inferencePayee` immutable) | 없음 | **추가**(약 2줄) |

- 변경 규모는 **약 30\~40줄**로 추정한다. Solidity를 할 줄 아는 사람이 없어도 필수다. 없으면 P3가 가장 먼저 붙는다.
- **Foundry 테스트 목록:**
  1. 정상 흐름: fund → open → settle → topUp → settle → close → refund
  2. Denied 5종: 벤더, 예산+수수료, `maxHold`, 기한, 일시정지. 각각 자금 이동 0과 이벤트 확인
  3. hold 초과 정산 → Denied
  4. 일시정지 뒤 창업자 settle과 close
  5. 기한 뒤 창업자 경로
  6. 열린 hold가 있을 때 `refund` 한도
  7. `recordDecision`의 `NO_JOB`
  8. INFERENCE 수수료 면제
  9. 권한 없는 호출과 닫힌 작업의 revert
  10. 벤더 이동(close A → open B)

### 기록과 해시
- 결정 기록은 JSON 파일 하나다. 한 번 직렬화해 저장한 **파일 바이트 그대로** keccak256한 값이 `recHash`다.
- 각 기록에는 `prevHash`, 읽기 단계에서 얻은 체인 값과 블록 번호, 게이트 입력과 판정, Qwen 원문 응답과 Kiln generation id·usage가 들어간다.
- 모든 tx가 자기 기록의 `recHash`를 이벤트로 남기므로 체인 머리가 계속 온체인에 고정된다.

**장부 항목과 tx 매칭**
| 장부 항목 | 온체인 |
|---|---|
| `fund`, `setVendor`, `setMaxHold`, `setPaused`, `open`, `topUp`, `settle`, `close`, `refund`, `recordDecision` | **tx 1:1**(Basescan 링크) |
| Kiln 호출 로그, 체크포인트 로그, 읽기 스냅샷 | tx 없음. 가장 가까운 tx의 기록 체인에 포함 |

**영수증 필드**
작업 ID, 벤더(Akash 제공자 라벨), 가격 출처(스냅샷 해시), 사용 시간, 금액, 수수료, 누적 gross, tx 해시, Qwen 사유, F3 설명.

### 사후 검증 명령 (USER 재판정)
- **입력:** 기록 파일 묶음, 금고 주소, 공개 RPC, 창업자 서명 명세.
- **소비하는 이벤트:** `Funded`, `VendorSet`, `MaxHoldSet`, `HoldOpened`, `ToppedUp`, `Settled`, `Closed`, `PausedSet`, `Refunded`, `Denied`.
- **검사 항목:**
  1. 모든 `recHash`가 기록 파일 바이트의 keccak과 같고, `prevHash` 체인이 끊기지 않았는가.
  2. 명세 서명자가 금고 `founder`인가.
  3. 모든 `HoldOpened`와 `ToppedUp` 앞에 게이트 PASS 기록과 Qwen 비거절 기록이 있는가.
  4. **결정적 게이트 규칙을 다시 계산했을 때** 기록의 판정과 같은가. 입력은 기록된 체인 읽기 값과 해당 블록의 체인 상태다.
  5. 지급 벤더가 지급 시점에 허용 목록에 있었는가.
  6. 누적 gross가 예산 이하이고, 수수료가 3%(INFERENCE는 0)인가.
  7. 에이전트의 `open`/`topUp`/`settle` 성공 tx가 기한 전, 일시정지 전인가. 에이전트 `close`와 `recordDecision`은 제외한다.
  8. 모든 `Denied` 이벤트에 대응하는 기록이 있는가.
- **범위 밖:** 정산 금액이 실제 사용량과 같은지, Qwen 기록이 진짜 Kiln 응답인지. Kiln generation id는 참고용으로만 남긴다.
- 심사위원이 재현하는 방법은 **사후 검증 명령(`npm run audit`)을 기록 묶음에 돌리는 것**이다(필수). 대시보드 리플레이는 선택이다.

### Kiln 흐름과 효율
| 흐름 | 트리거 | 입력 → 출력 | 표시 위치 |
|---|---|---|---|
| F1 `work_request` | 작업 시작, 충전 트리거 | 명세 + 진행 로그 → 요청 JSON(벤더·GPU·금액·근거) | 대시보드 요청 카드 |
| F2 `cfo_review` | 게이트 통과 후 | 명세 + 요청 + 요약 → `{verdict, reason}` | 결정 기록, 대시보드 |
| F3 `receipt_explain` | 작업 close | 작업 기록 요약 → 설명 2\~3문장 | 영수증 |

- **실제 호출 증거:** 최종 증거는 반드시 실제 Kiln 응답이어야 한다. 원문 응답, `usage`, generation id를 JSONL로 남긴다. stub LLM은 개발에만 쓴다.
- **응답이 결정을 바꾸는 장면:** F2의 `deny`가 `recordDecision`을 거쳐 `Denied` 이벤트로 남는 과정을 로그로 이어서 보여준다.
- **흐름별 표:** JSONL을 읽어 F1/F2/F3별 호출 수, 입력·출력 토큰, 비용, 에너지를 표로 만드는 스크립트를 둔다.
- **절감 근거(필수):**
  - 게이트가 먼저 거절해서 F2를 부르지 않은 건수와 절약한 토큰
  - `/no_think` 켬/끔 비교 3회
- **"모든 결정을 LLM이" 기준선(선택):** 기록된 요청을 규칙을 넣은 프롬프트로 F2에 오프라인 재실행하는 가장 작은 형태로만 한다. 체인에는 올리지 않는다.
- **에너지:** `E = Σ 출력 토큰 × 1.63 J`.
  - 근거: Furiosa 블로그(2026-04-02). RNGD 8장 서버 3 kW ÷ (46명 × 40 tok/s). 같은 조건의 RTX Pro 6000은 4.02 J.
  - 가정: 정격 전력, 전부하, PUE 제외, **prefill(입력) 토큰 제외**.
  - 상한 참고값: 배칭이 없을 때 RNGD 4장(각 180W)을 요청 하나가 독점하면 720W ÷ 60.6 tok/s(Kiln 공개 속도) ≈ 11.9 J.
  - Kiln의 실제 서빙 구성은 알 수 없다.

### 알려진 한계 (README에 명시)
- **정산 금액은 우리 장부가 신고한 값이다.** 체인은 실제 사용량을 검증하지 않는다. 벤더와 공모하면 hold 한도 안에서 샐 수 있다.
- **Qwen 판단과 기록은 백엔드가 스스로 증명한 값이다.** Kiln 서명이 없다. USER는 사후 검증으로 결정적 규칙은 다시 계산할 수 있지만, Qwen 판정 자체의 진위는 확인할 수 없다.
- **탈취된 agent 키**는 허용 벤더에게 금고의 미지급 잔액 전체(budget − Σpaid, 열린 hold 포함)까지 보낼 수 있다. `maxHold`는 open/topUp 1회 상한일 뿐이다. 규칙 위반 시도는 `Denied`로 체인에 남고, STOP 이후에는 아무것도 나가지 않는다. 또 규칙 안에서 진행 중인 job을 close하거나 남은 예산을 쓸모없는 hold로 묶어 세션을 방해할 수 있다(SEC-2). 이때는 STOP 후 windDown한다.
- **gas(ETH)는 USDC 예산 한도 밖이다.** 장부에만 기록한다.
- **벤더 가격은 과거 bid 기반 추정치**이고 확정 견적이 아니다. `debug=true`는 문서에 없는 옵션이라 스냅샷 JSON을 fallback으로 둔다.
- **INFERENCE 정산은 상환 회계다.** 실제 Kiln 과금은 오프체인 크레딧으로 이루어진다.

### 리뷰 수정 사항 (승인된 동작 변경 없음)

아래는 승인된 동작을 바꾸지 않는 수정이다. 일관성과 명확성을 맞추거나, 누가 봐도 빠진 부분을 채운다.

#### 컨트랙트 (문서의 "필요한 변경" 표와 테스트 목록에 추가)
- **open은 모든 검사를 `jobs.push` 전에 끝낸다.** 거절되면 `Denied(NO_JOB, code, rec)`를 남기고 `NO_JOB`을 반환한다. `topUp`과 `settle`은 `returns (bool)`로 바꾼다. 163행의 "false 반환"을 "open은 NO_JOB, topUp/settle은 false"로 고친다. [S1-4, S2-10, S6-6, S10-2]
- **검사 순서를 한 줄로 고정하고 게이트도 같은 순서를 쓴다:** AUTH(revert) → id 존재(없으면 `revert JobClosed`, 새 에러는 만들지 않음) → closed(revert) → PAUSED → PAST_DEADLINE → VENDOR_NOT_ALLOWED → OVER_MAX_HOLD(gross 계산 전에 net 원금으로 비교해 Panic 0x11 방지) → OVER_BUDGET_WITH_FEE / OVER_HOLD. 규칙을 여러 개 어기면 첫 코드 하나만 낸다. [S1-5, S2-10, S3-14, S5-2, S6-7, S10-2]
- **Denied 코드는 enum을 쓰지 않고 `bytes32` ASCII 문자열로 한다**(`bytes32("PAUSED")` ↔ `stringToHex(c,{size:32})`). 목록은 `codes.ts` 한 곳에 두고, Solidity는 같은 리터럴을 쓴다. [S1-5, S5-2, S8-8, S11-7]
- **이벤트 시그니처:** `Denied(uint256 indexed jobId, bytes32 indexed code, bytes32 indexed rec, bool enforced)`. HoldOpened/ToppedUp/Settled의 `recordHash`도 indexed로 바꾼다. enforced는 규칙 검사 경로면 true, recordDecision이면 false다. [S8-1, S8-8, S3-7]
- **`close(id, rec)`, `refund(amount, rec)`로 바꾸고 Closed/Refunded 이벤트에 rec를 넣는다.** 세션의 마지막 tx는 "세션 종료 기록"을 앵커하는 refund다. 201행은 "open/topUp/settle/close/refund/recordDecision/setPaused가 recHash를 남긴다. fund/setVendor/setMaxHold는 tx 해시로 매칭한다"로 좁힌다. [S1-6, S2-8, S3-4, R3-5]
- **`recordDecision`은 agent 또는 founder만 호출할 수 있고, 그 외는 revert Unauthorized로 한다.** [S3-7]
- **166행 revert 목록을 완성한다:** Unauthorized, JobClosed(없는 id 포함), refund 한도 초과 OverBudget, 토큰 전송 실패. [S6-6]
- **보안 주장 문구를 사실에 맞춘다.** 91\~92·165·250행을 "권한 있는 호출자의 규칙 위반만 Denied로 남는다. 권한 없는 함수 호출은 revert되고 대개 브로드캐스트조차 되지 않는다. 총 손실 상한은 maxHold가 아니라 `budget − committed`다"로 고친다. [R3-20, S3-5, S3-7, S11-7]
- **금액 기준을 하나로 정한다:** open/topUp/settle의 `amount`는 **net**이고, 예약은 `gross(v,a) = v==INFERENCE ? a : a + a*300/10000`(floor)이다. OVER_MAX_HOLD는 net ≤ maxHold, OVER_BUDGET은 committed + gross ≤ budget로 판정한다. 게이트, 실행기, 사후 검증 코드는 `rules.ts`의 bigint `gross/maxNet`을 공유한다. `maxNet(h)`는 gross(n) ≤ h를 만족하는 최대 n이다(시작값 floor(h·10000/10300), ±1 보정). 150행의 "×1.03"을 이 식으로 교체한다. [R3-12, S2-11, S4-7, S6-4, S9-4]
- **`fund`는 deadline을 덮어쓰므로 모든 스크립트가 `cfg.deadline`을 명시적으로 넘긴다**고 적는다. [S9-3, S4-8]

#### 백엔드 쓰기 경로와 결과 판정
- **모든 쓰기는 `commit(intent)` 하나로만 한다**(Promise 체인 큐). 한 단위의 순서: head 읽기 → compact JSON 직렬화(bigint와 NaN은 문자열, 들여쓰기·끝 개행 없음) → 쓴 Buffer 그대로 keccak → tmp+rename → 다시 읽어 해시 확인(실패 시 HALT, tx 없음) → ledger `intent` → send → txHash를 즉시 `sent`로 기록 → receipt → `classify` → `mined` → head 갱신. 매 tx마다 receipt를 기다리므로 nonceManager는 필요 없다. Kiln/게이트 계산은 큐 밖에서 병렬로 돌려도 된다. [S1-1, S2-6, S7-1, S8-2, S6-2, S3-13]
- **tx가 안 잡힐 때 정책:** 60초 타임아웃 → 같은 해시로 1회 재조회 → 그래도 없으면 HALT와 UNCONFIRMED 배너. **새 nonce로 다시 보내는 것은 금지**다(이중 지급 위험). 자동 수수료 인상 재전송은 만들지 않는다. (충돌 해소: S1-7·S8-6의 자동 교체 대신 S2-16·S5-6을 택함) [S2-16, S6-10 A, S5-6]
- **`classify(receipt)`를 단일 판정 지점으로 둔다.** 금고 주소의 로그만 ABI로 디코드한다. 기대한 이벤트가 있으면 OK, Denied가 있으면 DENIED(code)로 [거절] 경로에 보낸다. status 0이면 REVERTED, 둘 다 없으면 UNEXPECTED로 HALT한다. 전송 전 revert는 errorName으로 가른다(JobClosed이고 실제로 closed면 ALREADY_CLOSED). jobId는 HoldOpened 로그에서만 얻는다. 오프체인에서 승인했는데 체인이 Denied로 돌려준 경우는 `CHAIN_DENIED` 기록(prev=승인 기록)을 남기고, 사후 검증에서는 이를 `CHAIN_OVERRIDE`로 분류한다(FAIL 아님). [R3-8, S2-9, S4-3, S8-1, S11-1]
- **chain watcher는 1개만 둔다.** 블록 N을 고정하고 multicall 1회로 paused, deadline, budget, committed, maxHold, feeBps, vendorAllowed, jobs[id]와 block timestamp를 읽어 snapshot을 만든다. 게이트, 실행기, 대시보드가 이 snapshot을 공유한다. 읽기가 실패하면 READ_FAILED(fail-closed)로 처리하고, snapshot이 10초를 넘기면 STALE_CHAIN으로 사용량 누적을 멈춘다. 게이트의 "현재"는 블록 타임스탬프다. [S1-3, S4-4, S2-17, S7-3, S8-6, R3-10, R3-13]
- **job 상태 머신 `next(state, event)`을 순수 함수로 둔다.** 상태는 NO_JOB/OPEN/RUNNING/AWAITING_TOPUP/HOLD_EXHAUSTED/STOPPED/CLOSED이고, 충전 요청 latch는 none/inflight/denied다. 불법 전이는 throw한다. 전이는 디코드된 이벤트로만 일어난다. STOPPED는 CLOSED까지 유지하고, unpause나 늦게 온 ToppedUp은 무시한다. paused, deadline, NaN은 **매 tick**(AWAITING 포함) 확인한다. 비동기 흐름은 epoch를 들고 다니다가, epoch가 바뀌었으면 CANCELLED로 끝내고 tx를 보내지 않는다. 충전 흐름이 60초를 넘으면 TOPUP_TIMEOUT으로 거절한다. [S4-1, S2-15, S5-4, S6-4, R3-14]
- **트리거 정의:** "현재 hold"는 마지막 open/topUp의 gross(고정값)다. `remaining = held − gross(unsettled_net)`이고, 트리거는 `remaining*10 < holdSize*4 && latch==none`일 때 한 번만 발화한다(엣지 트리거). unsettled는 Settled를 디코드했을 때만 줄인다. [S4-2, S2-2, S6-4, S4-3]
- **실행기 정지 기준:** `unsettled_net ≥ maxNet(held)`이면 정지하고, settle 금액은 `min(accrued, maxNet(held))`다. 기한은 체인 시간 기준 `deadline − 15s`에 멈춘다. 기한 Denied 시연을 위해 margin을 끄는 플래그를 하나 둔다. [S4-7, S4-8, S2-11]
- **R3-13 단위 정의:** 요청 시간(sim h) = net 금액 ÷ 시간당 net 가격, real_s = sim_h × 60이다. 예시: B $2.56/h에서 $5.12 요청 = 2 sim h = 120 real s이므로 `blockTs + 120 > min(명세 기한, 금고 기한)`이면 PAST_DEADLINE이다. 110행을 이 식으로 교체한다. [R3-13]
- **OVER_JOB_CAP 누적은 job id가 아니라 `spec_id` 단위로 센다**(이동해도 초기화되지 않음). [R3-11]
- **명세 필드에 `spec_id`, `vault`, `chain_id: 84532`, `issued_at`을 추가한다.** 서명 대상은 저장된 파일 바이트 그대로의 문자열이고, 사후 검증에서는 이를 다시 직렬화하지 않는다. 같은 spec_id를 두 세션에 쓰면 FAIL이다. [R3-16, S3-9]
- **세션 종료를 함수 하나(`windDown`)로 정의하고 [종료], [STOP], [기한]이 모두 이 함수를 쓴다.** 순서: vendor job마다 `delta_net = 장부 사용량(실행기 정지 시점까지) − 체인 Settled 합`, delta가 0보다 크면 settle하고 디코드 → close → INFERENCE settle(누적 추론비) → close → refund(budget − committed, rec=세션 종료 기록). 이미 closed인 job은 건너뛰므로 다시 실행해도 안전하다. "정지 시점"은 **실행기가 멈춘 시점**이다. F3는 vendor job이 close될 때마다 돌고, INFERENCE 정리는 세션 끝에 한 번만 한다. [R3-3, R3-4, R3-5, R3-14, S11-2, S8-6]
- **창업자 버튼 가드:** 정산·close는 job이 STOPPED나 HOLD_EXHAUSTED이고 그 job의 pending tx가 0일 때만 활성화한다. 금액은 서버가 계산하고 클라이언트 값은 쓰지 않는다. close는 unsettled==0일 때만 보낸다. settle 없이 close된 사용량은 `UNPAID_USAGE`로 표시한다. [S4-6, S11-2]
- **대시보드 액션:** `POST /action {type, jobId, stateVersion}`로 보낸다. 같은 액션이 pending이거나 stateVersion이 오래됐으면 409를 돌려준다. 버튼은 누르면 잠기고 이벤트를 디코드한 뒤 풀린다. approve는 정확한 금액만 한다. [S4-9]
- **이동 순서를 대본에 고정한다:** settle(A) → close(A) → setVendor(A,false) → F1/게이트/F2 → open(B). 트리거는 scenario 스텝으로 주입하고, 기록에 `overrides[{field, from, to, by:"scenario:…"}]`와 그 시점의 Akash 실제 값을 남긴다. [S4-10, S8-7, S7-5]

#### LLM·Akash 어댑터
- **parse.ts 규칙:**
  - `finish_reason==length`면 Truncated로 보고 재시도하지 않는다.
  - `<think>`와 코드펜스를 벗긴 뒤 **남은 문자열 전체를** JSON.parse한다. JSON 객체가 2개 이상이면 UNPARSEABLE이다.
  - F2 verdict는 `trim().toLowerCase()==='approve'`일 때만 통과한다. `deny`면 QWEN_DENIED, 그 밖의 값은 전부 QWEN_UNPARSEABLE이다.
  - F1은 모양만 검사한다. vendor 라벨은 문자열이면 되고, 모르는 라벨은 게이트로 넘겨 VENDOR_NOT_ALLOWED를 받게 한다. amount는 양수이고 소수 6자리 이하이며, 어기면 QWEN_UNPARSEABLE이다.
  - F1/F2는 `/no_think`와 max_tokens 512, F3는 256으로 둔다. `/no_think` 비교는 오프라인 스크립트로 돌린다.
  - (충돌 해소: S3-8의 `allow`를 버리고 `approve`로 통일. F1 enum을 엄격 검사하면 주입 장면이 사라지므로 S2-4의 "모양만 검사"를 택함) [S2-1, S2-4, S3-8, S4-5, S6-8]
- **F2 입력 격리와 요청 불변식:** F2에 넣는 것은 명세 원문, 코드가 계산한 숫자 요약, F1의 구조화 필드뿐이다. rationale은 300자 이하로 `<untrusted_rationale>`에 감싼다. 원시 로그와 Akash 텍스트는 넣지 않는다. 게이트 입력 R은 `Object.freeze`하고 hash(R)를 기록한다. **tx 인자는 R에서만 만든다.** [S3-3]
- **F3는 close가 디코드된 뒤 비동기로 돈다.** 실패하면 "설명 생성 실패(코드)"를 적고 정산은 계속한다. [S2-4, S6-8, S11-12]
- **kiln.ts는 SDK 없이 `fetch` + AbortSignal로 만든다.** generation id는 `X-Neocloud-Generation-Id` 헤더에서 읽는다. 실패한 시도까지 전부 `{flow, attempt, http, latency_ms, gen_id, usage|null, cost_known, messages, llm_mode}`로 남긴다. JSONL에는 허용한 필드만 쓰고 헤더, 에러 객체, 절대경로는 넣지 않는다. 프로세스 전역 세마포어는 4다. usage.cost는 세션 끝에 합산한 뒤 ceil(sum·1e6)을 한 번만 한다. [S2-3, S3-1, S7-7, S2-11, S6-8]
- **`LLM_MODE=kiln|stub`은 반드시 명시하게 한다**(기본값 없음, 자동 fallback 없음). stub의 gen_id는 `stub-`로 시작한다. `audit --submission`은 stub 호출이 1건이라도 있으면 FAIL이다. [S8-5, S1-7]
- **Akash:** 세션 시작 때 한 번만 조회한다(타임아웃 5초). h100 존재, providersWithBestBid 3개 이상, price가 유한하고 0.5\~20 범위인지 검증하고, 실패하면 커밋된 스냅샷을 쓴다. 가격과 가용 수량은 세션 동안 고정한다. A/B/C는 hostUri로 고정한다. 스냅샷 **내용**을 번들 `prices/`에 넣고, 기록에 `price_source=LIVE|SNAPSHOT:사유`를 남긴다. [S2-5, S7-5, R3-10]

#### 사후 검증
- **과거 상태는 이벤트 재생으로 복원하고, archive eth_call에 기대지 않는다.** getLogs는 금고 주소 필터만 걸고 **1,000블록 청크**로 나눠 읽는다(sepolia.base.org 실측 한도). 입력 번들은 `{vault, chainId, deployBlock, lastBlock}`이다. 종료 코드는 0 PASS / 1 FAIL / 2 CANNOT_VERIFY다. 번들의 모든 tx 해시에 대해 receipt를 다시 확인한다. (충돌 해소: 2,000블록이 아니라 실측값 1,000) [R3-10, S2-13, S7-4, S6-3, S11-13]
- **사후 검증의 분류 규칙:**
  - 기록이 없는 Denied는 `UNRECORDED_ATTEMPT` WARN이다(PASS 유지, sender·code 출력).
  - 기록이 없는 HoldOpened/ToppedUp/Settled는 `UNGATED_SPEND` FAIL이다.
  - 마지막 기록의 해시가 마지막 온체인 rec와 다르면 `UNANCHORED_TAIL` FAIL이다.
  - 같은 recHash를 둘 이상의 이벤트가 참조하면 `DUPLICATE_REC_REF`로 표시한다.
  - 성공기준 1의 1:1 매칭은 백엔드·founder tx로 한정하고, 공격 tx는 별도 목록으로 낸다. [R3-7, S3-7, S2-8, S6-3]
- **check 7 재정의:** agent가 보낸 tx 중 HoldOpened/ToppedUp/Settled를 낸 것에 대해, 그 블록에서 paused==false이고 blockTs < deadline이었는지 본다(재생 상태 기준). [R3-9]
- **check 4:** `rules.check(rec.gateInput)`의 결과가 rec.gateResult와 같은지, 그리고 gateInput의 체인 필드가 재생한 상태와 같은지 본다. check 3은 `parseVerdict(extractJson(rec.raw))`를 다시 계산해 비교한다. 사후 검증 코드는 rules/parse/records/chain(읽기 쪽)만 import하고, executor/kiln/akash/server는 import하지 않는다(grep 한 줄로 테스트). [R3-19, S5-1, S5-3]
- **LOSS_PLATEAU 정의:** 연속 3쌍 모두 (prev − cur)/prev < 0.005일 때만 plateau다. 체크포인트가 4개 미만이거나 prev ≤ 0이면 false다. NaN은 NAN_DETECTED가 먼저 잡는다. [S5-3, S6-7]

#### 4. 비동기 순서: STOP과 topUp, settle과 close/pause
```
 순서 A: pause가 먼저 착지
   backend: read@N paused=0, gate PASS, F2 ... | founder: setPaused(true) -> N+3 PausedSet
   watcher@N+3 -> STOPPED(유지)  (epoch 불일치면 CANCELLED, tx 없음)
   이미 보낸 topUp -> N+5: Denied(PAUSED), 이동 0 -> CHAIN_DENIED(=CHAIN_OVERRIDE), 재개 안 함
 순서 B: topUp이 먼저 착지 (N+3 idx0 ToppedUp, idx1 PausedSet)
   watcher -> STOPPED (ToppedUp이 와도 재개 안 함) -> agent settle Denied(PAUSED)
   -> founder settle(delta) -> close(늘어난 held 해제) -> INFERENCE -> refund
 어느 쪽이든: pause 이후 돈이 나가지 않고 committed <= budget (tx마다 원자적 _agentChecks)

 settle과 close/pause 경합
 (i)  agent settle(u) vs founder close: close가 먼저면 settle은 revert JobClosed -> u 미지급
      막기: 같은 commit 큐 + close는 pending 0 && unsettled==0일 때만
 (ii) agent settle vs setPaused: pause가 먼저면 Denied -> unsettled 유지(Settled 디코드 시에만 감소) -> founder delta
 (iii) agent settle vs agent close: nonce 순서로 고정. 그래도 close는 Settled 디코드 뒤에만
 (iv) 기한 직전 대기 중 settle vs founder 정산: 금액은 큐가 빈 뒤 서버가 delta_net으로 계산
```
