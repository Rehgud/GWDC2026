## Problem Statement

GPU를 빌려 쓰는 AI 스타트업의 연구·평가 에이전트는 이미 API로 GPU를 직접 띄운다(RunPod 공식 MCP, io.net Agent Cloud). 그런데 에이전트 단위로 "얼마까지, 어느 벤더에, 언제까지"를 강제하거나, 나중에 그 허락을 검증할 방법은 없다. 결제 레일은 누가 누구에게 냈는지만 기록하고, 누가 어떤 조건으로 허락했는지는 기록하지 않는다.

CFO Agent는 이 지출을 **작업 단위로 충전하고 감독하는 에스크로 금고**다. 금고는 Base Sepolia 컨트랙트로 구현한다. 허용 벤더, 수수료 포함 예산, 호출당 상한, 기한, STOP은 체인이 강제한다.

제3자는 기록과 체인만 보고 세 가지를 다시 판정할 수 있다.
1. 각 지출이 **결정적 규칙**을 지켰는지: 벤더, 예산, 상한, 기한, STOP, 허용 GPU. 기록에 남은 입력값과 체인 상태로 게이트 규칙을 다시 계산한다.
2. 모든 hold와 충전 앞에 게이트 통과와 CFO 비거절 기록이 있는지.
3. 기록이 변조되지 않았는지.

범위 밖인 것도 있다. **정산 금액이 실제 GPU 사용량과 같은지**, 그리고 **Qwen 판단 기록이 실제로 Kiln이 낸 응답인지**(백엔드가 스스로 증명하는 값)는 검증하지 못한다. 한계 절을 참고한다.

해커톤 제출용이다. GWDC 2026 Korea, FuriosaAI × Bricksum Agent Finance 트랙, 권장 과제는 Challenge B다.

## What Makes This Cool

- **돈이 나가는 도중에 충전을 심사한다(헤드라인).** 결제 한 건을 막는 게 아니다. 작업이 진행되는 동안 잔액이 줄면 작업 에이전트가 충전을 요청하고, CFO Qwen이 목적에 맞는지 심사한다. 규칙은 통과했지만 목적을 벗어난 충전은 Qwen이 거절한다.
- **Akash mainnet의 결제 규칙을 EVM으로 옮겼다.** 대응 관계는 다음과 같다.
  - `fund` → AccountDeposit(예치)
  - `open` → CreateLease
  - `topUp` → AccountDeposit(충전)
  - `settle` → WithdrawLease
  - `close` → CloseLease
  - `refund` → CloseDeployment 시 남은 예치금 환불
- **벤더 가격이 실제 시장 가격이다.** Akash Console API `/v1/gpu-prices?debug=true`를 인증 없이 호출해 제공자별 대표 입찰가를 받는다. 최근 31일 온체인 bid를 GPU 1개당 시간당 USD로 환산한 값이다. 이 가격을 H100 제공자 세 곳에 붙여 벤더 A/B/C로 쓴다(예: $2.04 / $2.56 / $3.16). 벤더 자체와 실행은 mock이다.
- **추론비도 같은 금고에서 정산한다.** Kiln 추론비(`usage.cost`)를 작업 종료 때 같은 금고에서 INFERENCE 수취 주소로 정산하므로, 추론비도 온체인 예산 한도 안에 들어간다. 호출 1회는 약 $0.00014라서 절감 효과를 내세우는 기능은 아니다. 통제자도 같은 한도 안에서 감사받는다는 점을 보여주는 장치다.

## Premises

1. GPU 벤더는 mock이다. 가격만 Akash 실데이터이고, 실행은 시뮬레이션이다.
2. 숫자 신호(loss 정체, NaN, 예산, 기한, 용량, 허용 GPU)는 코드가 판단한다. CFO Qwen은 요청이 승인된 목적에 맞는지, 근거가 타당한지, 범위가 넓어지고 있지 않은지를 판단하고 사유를 작성한다.
3. 작업 하나에 GPU 벤더 하나. 벤더 이동은 체크포인트를 거쳐 대본대로 1회만 시연한다. mock 벤더들은 결제 방식이 같다.
4. 충전 hold는 금고에 실제로 잠긴다(`committed`). 체크포인트마다 벤더 실사용분을 정산 tx 1건으로 처리하고, 기록 해시를 체인에 고정한다.

## Approaches Considered

### Approach A: 시간 블록 — 채택 안 함
같은 금고를 쓰고 호출 주기만 1시간 단위로 바꾸는 방식이다. 시뮬레이션 시계는 A와 B 모두 필요하다. A를 버린 이유는 두 가지다. 변화가 없어도 블록마다 심사하느라 토큰을 쓰고, "블록이 끝나면 작업도 끊기나" 하는 개념적 혼란을 만든다.

### Approach B: 에스크로 금고 + 충전식 — **채택**
아래 Recommended Approach 참고.

### Approach C: 마일스톤 결제 — 채택 안 함
마일스톤마다 비용 추정이 필요하고, 시간 단위 과금으로 바꾸는 작업이 따로 든다.

### 제외한 결제 방식 (한 줄씩)
- **Akash 실제 사용:** 테스트넷에서 응답하는 GPU 제공자가 1곳뿐이고, Cosmos 스택이 추가로 필요하다(10~16h). 가격만 가져온다.
- **x402 exact:** 수신자를 체인에서 제한할 수 없다. 벤더 1곳을 x402 `upto`로 정산하는 것은 stretch로 둔다. upto는 돈을 잠그지 않으므로 hold로 부르지 않는다.
- **Superfluid:** 잔액이 0이 되면 청산되면서 buffer를 잃는다.
- **approve / Spend Permissions / Safe allowance:** 수신자를 체인에서 제한할 수 없다.

## Recommended Approach

**Akash식 에스크로 금고(Base Sepolia, MockUSDC) + 충전식 주기 + Akash 실가격 벤더 A/B/C.**

### 등장 주체와 키
| 주체 | 정체 | 호출 가능 함수 |
|---|---|---|
| 창업자(ML 리드) | founder 지갑 | `fund`, `setVendor`, `setPaused`(STOP), `setMaxHold`, `refund`. **일시정지나 기한 이후에도** `settle`, `close` 가능 |
| 에이전트 백엔드 | agent 키(서버 hot key) | `open`, `topUp`, `settle`, `close`, `recordDecision` |
| 벤더 A/B/C | 팀이 만든 EVM 주소. 각각 Akash 제공자 1곳의 hostUri와 가격 스냅샷으로 라벨링 | 수취만 |
| INFERENCE | 팀의 Kiln 크레딧 상환 주소. 허용 목록에 포함 | 수취만 |
| feeTo | 마켓 수수료 수취 주소 | 수취만 |

- **agent 키를 탈취당하면:** 허용 벤더에게만, 호출당 `maxHold` 이하로, 남은 예산 안에서만 hold/충전/정산할 수 있다. 일시정지 중이거나 기한이 지났으면 그것도 안 된다.
- 허용 목록 밖으로 보내기, 예산 초과, `refund`, 허용 목록 변경은 불가능하다. 위반 시도는 모두 `Denied` 이벤트로 체인에 남는다.
- 게이트 키 co-signature(EIP-712)는 stretch로 둔다.

### 작업 명세 (목적의 출처, 창업자 서명)
- 창업자가 작업마다 명세 JSON을 쓴다. 필드는 `purpose`, `success_metric`, `allowed_gpu_types`, `job_cap_usd`, `deadline`이다.
- 창업자 지갑으로 서명한다(EIP-191). 서명과 명세 해시는 첫 기록에 들어간다.
- 감사자는 서명자가 금고의 `founder`인지 확인한다. 백엔드가 명세를 바꾸면 여기서 FAIL이 난다.
- Qwen은 심사할 때마다 명세 원문을 입력으로 받는다.

### 시뮬레이션 시계와 데모 규모
| 항목 | 값 |
|---|---|
| 시계 | 실제 1초 = 시뮬레이션 1분 (60배) |
| 예시 요금 | H100(B) $2.56/h → 실제 1초에 약 $0.043 |
| 초기 hold | 1 시뮬레이션 시간분. gross = $2.56 × 1.03 ≈ $2.64 |
| 충전 트리거 | 잔액이 현재 hold의 **40% 미만** (실제 약 36초 시점). 소진까지 약 24초가 남으므로 F1, 게이트, F2(재시도 포함 최대 약 20초), tx 확인이 그 안에 끝날 수 있다 |
| 늦은 승인 | 심사 중에 hold가 소진되면 실행기는 **AWAITING_TOPUP 상태로 대기**한다. 사용량은 쌓이지 않는다. 승인되면 이어서 진행하고, 거절되면 종료 절차로 간다 |
| 체크포인트 | 30 시뮬레이션 분(실제 30초)마다, 그리고 충전·중단·종료 때 |
| 기한 | 실제 블록 시간 기준. 요청한 시뮬레이션 시간은 60으로 나눠 실제 초로 바꾼다. 적용 기한 = min(명세 기한, 금고 기한) |

### 흐름
```
[준비] 창업자: fund(예산, 기한) · setVendor(A,B,C,INFERENCE) · setMaxHold · 명세 서명
[읽기] 모든 요청 직전 백엔드가 eth_call로 budget, committed, paused, deadline,
       vendorAllowed, maxHold, jobs[id]를 읽고, 값과 블록 번호를 기록에 넣는다
[추론 hold] 세션 시작: open(INFERENCE, 소액) → 추론비 전용 작업
[시작] 작업 에이전트(Qwen F1): 명세를 보고 벤더·GPU·초기 hold 제안
       → 게이트(규칙) → CFO Qwen(F2, 게이트 통과 시에만) → open(vendor, hold, recHash)
[진행] mock 실행기: 사용량 누적(60배), 30분마다 체크포인트 → settle(vendor 작업, 실사용)
       매 체크포인트에서 paused와 기한을 읽고, 해당하면 [STOP]/[기한]으로 간다
[충전] 트리거 = 잔액 < 현재 hold의 40%
       → F1: 진행 상황 + 근거 + 충전액으로 요청 → 게이트 → F2 → topUp(id, 금액, recHash)
[이상] NaN → 즉시 체크포인트 → settle → close. 코드가 처리하고 Qwen은 호출하지 않는다
       loss 정체(최근 3개 체크포인트 개선 < 0.5%) → 이후 충전 요청을 게이트가 LOSS_PLATEAU로 거절
[거절] 게이트나 Qwen이 거절 → recordDecision(id 또는 NO_JOB, code, recHash)
       → 남은 hold까지만 진행 → 소진되면 실행기 정지(HOLD_EXHAUSTED)
       → 체크포인트 → settle(실사용) → close(남은 hold 해제)
[이동] 트리거: A의 가용 수량 0, 또는 가격 급등
       → 체크포인트 → settle(A) → close(A) → 창업자가 setVendor(A,false)
       → 게이트 → Qwen → open(B) → 체크포인트에서 재개
[STOP] 창업자 setPaused(true, 사유해시) → 실행기는 다음 체크포인트에서 정지
       → 이후 에이전트의 open/topUp/settle은 Denied(PAUSED)
       → 창업자가 settle(정지 시점까지 실사용) → close → refund(미약정 잔액)
[기한] 기한에 닿으면 실행기 정지 → 에이전트 호출은 Denied(PAST_DEADLINE)
       → 창업자(대시보드 버튼)가 settle(실사용) → close → refund
[종료] 작업 close 때 F3로 영수증 설명 → 추론 작업 settle(INFERENCE 누적 추론비) → close
       → 감사자 CLI PASS/FAIL
```
- **평가 순서:** 게이트가 먼저 판정하고, Qwen F2는 **게이트를 통과한 요청만** 판단한다. Qwen이 거절하면 그걸로 최종이다.
- 실행기는 hold 소진, STOP, 기한, NaN 가운데 하나라도 해당하면 멈춘다. 그래서 hold를 넘는 사용량은 생기지 않는다.
- **추론비 정산:** 수수료가 없다(INFERENCE 수취자는 fee 면제). 작업 개설 전이나 거절된 요청에서 쓴 추론비도 세션 시작 때 연 추론 작업의 hold에서 나간다.

### 코드 게이트 규칙
| 코드 | 규칙 | 입력 |
|---|---|---|
| `VENDOR_NOT_ALLOWED` | 벤더가 허용 목록에 없음 | 체인 `vendorAllowed`(읽기 단계) |
| `GPU_TYPE_NOT_ALLOWED` | 요청 GPU가 명세 `allowed_gpu_types`에 없음 | 서명된 명세 |
| `NO_CAPACITY` | 해당 GPU의 Akash 가용 수량이 0 | Akash 가격 캐시(스냅샷 해시를 기록) |
| `OVER_BUDGET_WITH_FEE` | committed + 금액×1.03 > budget | 체인 `budget`, `committed` |
| `OVER_MAX_HOLD` | 요청 금액이 `maxHold`를 넘음. open과 topUp 모두에 적용 | 체인 `maxHold`(데모 값 $6) |
| `OVER_JOB_CAP` | 작업 누적 gross가 명세 `job_cap_usd`를 넘음 | 장부, 명세 |
| `PAST_DEADLINE` | 현재 + 요청시간/60 > min(명세 기한, 금고 기한) | 체인 `deadline`, 명세 |
| `PAUSED` | STOP 상태 | 체인 `paused` |
| `LOSS_PLATEAU` | 최근 3개 체크포인트 개선이 0.5% 미만 | 실행기 로그 |
| `NAN_DETECTED` | loss가 NaN | 실행기 로그 |
| `QWEN_DENIED` / `QWEN_UNAVAILABLE` / `QWEN_UNPARSEABLE` | Qwen 거절 / 타임아웃·429 / 파싱 실패 | Kiln 응답 |

- **Qwen이 실패하면 거절한다(fail-closed).** 타임아웃은 20초다. 429·5xx나 파싱 실패는 1회 백오프 재시도한 뒤에도 실패하면 거절하고 기록한다.
- 체인이 강제하는 규칙(벤더, 예산, 상한, 기한, STOP)은 게이트와 컨트랙트가 **같은 코드 값**을 쓴다. 게이트에서 `VENDOR_NOT_ALLOWED`로 판정한 것은 컨트랙트에서도 `Denied(VENDOR_NOT_ALLOWED)`로 남는다.

### 컨트랙트: 거절 기록 방식 (Denied)
- **규칙 위반은 revert하지 않는다.** 돈을 움직이지 않고 `Denied(jobId, code, recHash)` 이벤트를 남긴 뒤 `false`를 반환한다.
  - 대상 위반: 벤더, 예산, `maxHold`, 기한, 일시정지, hold 초과 정산
  - 탈취 키의 시도까지 모든 멈춤이 체인에 남는다. 과제의 "멈춤은 조용하지 않고 기록되어야 한다"는 요구를 여기서 충족한다.
- **revert는 권한 없는 호출(`Unauthorized`)과 닫힌 작업(`JobClosed`)에만 쓴다.**
- 게이트나 Qwen이 tx를 보내기 전에 거절한 건은 `recordDecision(jobId 또는 NO_JOB, code, recHash)`로 같은 `Denied` 이벤트를 남긴다. `NO_JOB`은 `type(uint256).max`이고, 작업 개설 전 거절에 쓴다. 이때 요청 ID는 기록 파일 안에 있다.
- **일시정지·기한 이후 동작:**
  - 에이전트의 `open`/`topUp`/`settle` → `Denied`
  - 에이전트 `close`, `recordDecision` → 허용
  - 창업자의 `settle`/`close` → 항상 허용
  - `refund` → 미약정 잔액(`budget − committed`)만 돌려준다
- **수수료:** `feeBps = 300`(3%), 수취 주소는 feeTo, 정산 금액 기준이다. INFERENCE 수취자는 면제다. hold는 수수료를 포함한 gross로 예약한다. 불변식은 `committed(열린 hold + 지급된 gross) ≤ budget`이다.

| 항목 | 초안 상태 | 필요한 변경 |
|---|---|---|
| `fund`, `setVendor`, `setPaused(reasonHash)`, `refund(미약정 한도)` | 있음(동작 확인함) | 없음 |
| 창업자 `settle`이 일시정지·기한을 우회, `close`는 창업자·에이전트가 언제든 호출 | 있음 | 없음 |
| `settle`의 gross 기준 hold 초과 검사, 수수료 분배, 이벤트와 `recHash` | 있음(revert 방식) | 위반 시 revert → `Denied`로 변경 |
| `_agentChecks`, `_reserve`의 위반 처리 | revert | `Denied` 기록 후 `false` 반환으로 변경 |
| `Denied` 이벤트, `recordDecision`, `NO_JOB` | 없음 | **추가** |
| `maxHold` + `setMaxHold`(open과 topUp 모두 상한) | 없음 | **추가** |
| INFERENCE 수수료 면제(`inferencePayee` immutable) | 없음 | **추가**(약 2줄) |

- 변경 규모는 **약 30~40줄**로 추정한다. Solidity를 할 줄 아는 사람이 없어도 필수다. 없으면 P3가 가장 먼저 붙는다.
- **Foundry 테스트 목록:**
  1. 정상 흐름: fund → open → settle → topUp → settle → close → refund
  2. Denied 5종: 벤더, 예산+수수료, `maxHold`, 기한, 일시정지. 각각 자금 이동 0과 이벤트 확인
  3. hold 초과 정산 → Denied
  4. 일시정지 뒤 창업자 settle과 close
  5. 기한 뒤 창업자 경로
  6. 열린 hold가 있을 때 `refund` 한도
  7. `recordDecision`의 `NO_JOB`
  8. INFERENCE 수수료 면제
  9. 권한 없는 호출과 닫힌 작업의 revert
  10. 벤더 이동(close A → open B)

### 기록과 해시
- 결정 기록은 JSON 파일 하나다. 한 번 직렬화해 저장한 **파일 바이트 그대로** keccak256한 값이 `recHash`다.
- 각 기록에는 `prevHash`, 읽기 단계에서 얻은 체인 값과 블록 번호, 게이트 입력과 판정, Qwen 원문 응답과 Kiln generation id·usage가 들어간다.
- 모든 tx가 자기 기록의 `recHash`를 이벤트로 남기므로 체인 머리가 계속 온체인에 고정된다.

**장부 항목과 tx 매칭**
| 장부 항목 | 온체인 |
|---|---|
| `fund`, `setVendor`, `setMaxHold`, `setPaused`, `open`, `topUp`, `settle`, `close`, `refund`, `recordDecision` | **tx 1:1**(Basescan 링크) |
| Kiln 호출 로그, 체크포인트 로그, 읽기 스냅샷 | tx 없음. 가장 가까운 tx의 기록 체인에 포함 |

**영수증 필드**
작업 ID, 벤더(Akash 제공자 라벨), 가격 출처(스냅샷 해시), 사용 시간, 금액, 수수료, 누적 gross, tx 해시, Qwen 사유, F3 설명.

### 감사자 CLI (제3자 재판정)
- **입력:** 기록 파일 묶음, 금고 주소, 공개 RPC, 창업자 서명 명세.
- **소비하는 이벤트:** `Funded`, `VendorSet`, `MaxHoldSet`, `HoldOpened`, `ToppedUp`, `Settled`, `Closed`, `PausedSet`, `Refunded`, `Denied`.
- **검사 항목:**
  1. 모든 `recHash`가 기록 파일 바이트의 keccak과 같고, `prevHash` 체인이 끊기지 않았는가.
  2. 명세 서명자가 금고 `founder`인가.
  3. 모든 `HoldOpened`와 `ToppedUp` 앞에 게이트 PASS 기록과 Qwen 비거절 기록이 있는가.
  4. **결정적 게이트 규칙을 다시 계산했을 때** 기록의 판정과 같은가. 입력은 기록된 체인 읽기 값과 해당 블록의 체인 상태다.
  5. 지급 벤더가 지급 시점에 허용 목록에 있었는가.
  6. 누적 gross가 예산 이하이고, 수수료가 3%(INFERENCE는 0)인가.
  7. 에이전트의 `open`/`topUp`/`settle` 성공 tx가 기한 전, 일시정지 전인가. 에이전트 `close`와 `recordDecision`은 제외한다.
  8. 모든 `Denied` 이벤트에 대응하는 기록이 있는가.
- **범위 밖:** 정산 금액이 실제 사용량과 같은지, Qwen 기록이 진짜 Kiln 응답인지. Kiln generation id는 참고용으로만 남긴다.
- 심사위원이 재현하는 방법은 **감사자 CLI를 기록 묶음에 돌리는 것**이다(필수). 대시보드 리플레이는 선택이다.

### Kiln 흐름과 효율
| 흐름 | 트리거 | 입력 → 출력 | 표시 위치 |
|---|---|---|---|
| F1 `work_request` | 작업 시작, 충전 트리거 | 명세 + 진행 로그 → 요청 JSON(벤더·GPU·금액·근거) | 대시보드 요청 카드 |

- **흐름별 표:** JSONL을 읽어 F1/F2/F3별 호출 수, 입력·출력 토큰, 비용, 에너지를 표로 만드는 스크립트를 둔다.
- **절감 근거(필수):**
  - 게이트가 먼저 거절해서 F2를 부르지 않은 건수와 절약한 토큰
  - `/no_think` 켬/끔 비교 3회

- **에너지:** `E = Σ 출력 토큰 × 1.63 J`.

### 알려진 한계 (README에 명시)
- **정산 금액은 우리 장부가 신고한 값이다.** 체인은 실제 사용량을 검증하지 않는다. 벤더와 공모하면 hold 한도 안에서 샐 수 있다.
- **Qwen 판단과 기록은 백엔드가 스스로 증명한 값이다.** Kiln 서명이 없다. 감사자가 결정적 규칙은 다시 계산하지만, Qwen 판정 자체의 진위는 확인하지 못한다.

- **gas(ETH)는 USDC 예산 한도 밖이다.** 장부에만 기록한다.
- **벤더 가격은 과거 bid 기반 추정치**이고 확정 견적이 아니다. `debug=true`는 문서에 없는 옵션이라 스냅샷 JSON을 fallback으로 둔다.
- **INFERENCE 정산은 상환 회계다.** 실제 Kiln 과금은 오프체인 크레딧으로 이루어진다.

> The flow opens the inference job directly ('[추론 hold] 세션 시작: open(INFERENCE, 소액)'), with no gate or Qwen step. Auditor check 3 requires a gate PASS record and a Qwen non-deny record before every HoldOpened. An honest run therefore FAILs the audit on its first open.

**Remedy**

> Either exempt HoldOpened/ToppedUp to inferencePayee from check 3 (and say which gate rules apply to it, if any), or route the INFERENCE open through the gate with a recorded decision. Update check 3 and the flow to match.

### R3-2 — completeness

**Problem**

> The INFERENCE hold is only '소액'. No amount is given, and the document does not say what happens when accumulated Kiln cost exceeds it. A settle above the hold is Denied, so the reimbursement would silently fail at [종료], and no topUp path exists for the inference job.

**Remedy**

> State the INFERENCE hold amount and its sizing basis (e.g., expected calls × ~$0.00014 with margin). Define the overflow behavior: a topUp of the inference job, a cap that halts LLM calls, or a partial settle recorded as a known shortfall.

### R3-3 — completeness

**Problem**

> The [STOP] and [기한] paths settle, close, and refund only the vendor job. After a pause or the deadline, agent settle is Denied, so the INFERENCE settle in [종료] cannot run. The inference hold stays committed, and refund (budget − committed) excludes it.

**Remedy**

> Add a founder settle(INFERENCE, accrued cost) and close of the inference job to [STOP] and [기한], before refund.

### R3-4 — clarity

**Problem**

> [종료] fires '작업 close 때'. Taken literally, it runs on every job close, including close(A) during [이동] and the closes in [거절] and [이상]. That would settle and close the inference job mid-session, leaving no inference hold for the F1/F2 calls that precede open(B).

**Remedy**

> Split the triggers: F3 runs on each vendor-job close, and the INFERENCE settle/close runs once at session end. Define session end explicitly.

### R3-5 — completeness

**Problem**

> The normal-completion path [종료] ends at the auditor CLI with no refund step. Success Criterion 1 requires an E2E run from fund to refund, and only [STOP] and [기한] include refund.

**Remedy**

> Add founder refund(budget − committed) to [종료], after the inference job closes and before the auditor runs.

### R3-6 — completeness

**Problem**

> [거절] assumes a running hold ('남은 hold까지만 진행 → 소진되면 … settle → close'). A denial of the initial open (NO_JOB) or of the migration open(B), which comes after close(A), has no hold to run down, and no terminal path is defined for either case.

**Remedy**

> Define both outcomes: whether F1 may re-propose (e.g., vendor C) and how many times, or the session ends and goes to the session-end sequence (INFERENCE settle/close, refund).

### R3-7 — consistency

**Problem**

> Auditor check 8 requires a matching record for every Denied event. The stolen-key call in Success Criterion 3(iii) bypasses the backend, so its Denied event carries an attacker-chosen recHash with no record, and the demo run FAILs Criterion 4. Criterion 1's rule that every on-chain item matches a ledger entry 1:1 cannot hold for that attacker tx either.

**Remedy**

> Define how the auditor classifies a Denied event with no matching record (e.g., report it as an 'unrecorded attempt' with sender and code, and do not FAIL), and scope Criterion 1's 1:1 matching to backend- and founder-sent txs, with attacker txs listed separately.

### R3-8 — completeness

**Problem**

> Under the Denied model, a rule-violating open/topUp/settle is a status-1 tx that returns false. The document does not require the backend, ledger, or executor to decode receipt events. If a gate- and Qwen-approved topUp is Denied on-chain (for example, STOP lands in between), a status-only check would resume the executor on a hold that does not exist, and the ledger would record a settle that never paid.

**Remedy**

> Require every agent/founder tx result to be taken from the emitted event (HoldOpened/ToppedUp/Settled vs Denied). Route an on-chain Denied to the [거절] path and record it in the ledger.

### R3-9 — clarity

**Problem**

> Auditor check 7 tests 'open/topUp/settle 성공 tx'. Under the Denied model every call succeeds at the EVM level, so 'success' is undefined. '일시정지 전' also reads as 'before the first pause', which would misjudge txs sent after an unpause.

**Remedy**

> Define check 7 over agent-sent txs that emitted HoldOpened, ToppedUp, or Settled, and require each to be in a block where paused was false and block time was before the deadline.

### R3-10 — feasibility

**Problem**

> Auditor check 4 recomputes the gate rules against '해당 블록의 체인 상태', which needs historical eth_call at arbitrary past blocks. Public Base Sepolia RPCs are typically not archive nodes, yet Criterion 4 requires PASS with 'public RPC only'. The records also store only the hash of the Akash snapshot (NO_CAPACITY), and the time basis for recomputing PAST_DEADLINE is unstated.

**Remedy**

> Reconstruct historical vault state by replaying the consumed events (Funded, VendorSet, MaxHoldSet, PausedSet, HoldOpened, …) instead of historical eth_call, or name an archive RPC. Use block timestamp as the time basis. Include snapshot contents in the bundle, or limit check 4 to the chain- and spec-derived rules listed in the Problem Statement.

### R3-11 — completeness

**Problem**

> OVER_JOB_CAP checks '작업 누적 gross' against the spec's job_cap_usd, but [이동] closes job A and opens a new on-chain job B for the same spec. If accumulation is per job id, the cap resets on migration and total spend can reach twice the founder-signed job_cap_usd.

**Remedy**

> Define OVER_JOB_CAP accumulation per signed spec (logical task) across all on-chain jobs opened under it, and have the ledger and auditor key it that way.

### R3-12 — clarity

**Problem**

> The document never says whether the open/topUp amount argument is net or gross. OVER_BUDGET_WITH_FEE multiplies it by 1.03, which implies net, while '초기 hold gross ≈ $2.64' and 'hold는 gross로 예약' suggest gross. OVER_MAX_HOLD does not say which basis it compares against $6. The ×1.03 gate formula is also wrong for the fee-exempt INFERENCE job. Because the gate and contract must share code values and check 4 recomputes both, any divergence produces false Denied results or false audit FAILs.

**Remedy**

> State the argument basis and give one formula per rule, including the INFERENCE fee exemption. Use that formula identically in the gate, the contract, and the auditor.

### R3-13 — clarity

**Problem**

> PAST_DEADLINE uses '현재 + 요청시간/60', and the clock table says '요청한 시뮬레이션 시간은 60으로 나눠 실제 초로 바꾼다'. Dividing by 60 yields real seconds only if the requested time is in simulated seconds; simulated hours to real seconds is ×60. F1 also requests amounts ('충전액'), not durations, and the document never says how an amount becomes a requested time. A unit mistake here shifts the deadline check by orders of magnitude.

**Remedy**

> Define the requested time as amount ÷ gross hourly price (simulated hours) and the conversion as real_seconds = simulated_hours × 60. Show one worked example.

### R3-14 — completeness

**Problem**

> The executor reads paused and the deadline only at checkpoints ('매 체크포인트에서 paused와 기한을 읽고'; '[STOP] … 다음 체크포인트에서 정지'). That allows up to 30 real seconds (about $1.28 at vendor B's rate) of accrual after STOP, and past the deadline, which contradicts '[기한] 기한에 닿으면 실행기 정지'. '정지 시점까지 실사용' is ambiguous: it could mean the setPaused time or the executor halt time.

**Remedy**

> Have the executor check paused (or subscribe to PausedSet) and the known deadline on every tick, and halt immediately. Define the founder's settle amount as usage up to the executor halt.

### R3-15 — consistency

**Problem**

> The clock table says F2 takes 'F2(재시도 포함 최대 약 20초)' and that F1, gate, F2, and tx confirmation fit in the 24 s before exhaustion. The fail-closed rule is a 20 s timeout plus one backoff retry, so F2's worst case exceeds 40 s, and F1's own Kiln latency is not counted.

**Remedy**

> Correct the worst-case budget (F1 + up to 2×20 s F2 + backoff + tx). State that in the worst case the executor visibly enters AWAITING_TOPUP, or shorten the F2 timeout so the claim holds.

### R3-16 — completeness

**Problem**

> The founder signs the spec with EIP-191, and check 2 verifies only that the signer is the vault founder. The signed payload is not bound to a vault address, chainId, or job/spec nonce. A compromised backend can substitute a different genuine founder-signed spec, such as an older one with a larger job_cap_usd or broader purpose, and still pass.

**Remedy**

> Include vault address, chainId, and a unique spec id/nonce in the signed payload. Have the auditor verify them and verify that each job references exactly one spec.

### R3-17 — clarity

**Problem**

> Success Criterion 2's deadline case uses '기한을 짧게 잡은 금고', which implies a second vault deployment. The auditor input, the matching table, and Criterion 1 all describe a single vault, so it is unclear how the deadline case is audited and matched.

**Remedy**

> State that the deadline demo runs on a second vault with its own bundle and auditor run, or trigger it on the main vault through the spec deadline and a founder-set deadline.

### R3-18 — clarity

**Problem**

> Success Criterion 3(ii) requires an injection that fools F1, but F1's inputs are the signed spec and progress logs, and no untrusted channel is named. The demo cannot be scripted without deciding where the attacker-controlled text enters.

**Remedy**

> Name the injection vector (e.g., a poisoned executor log line or vendor/provider metadata field fed to F1) and the out-of-bounds request it is meant to produce.

### R3-19 — feasibility

**Problem**

> Auditor check 4 must recompute the same deterministic rules as P1's gate check(). The document does not say whether the auditor (owned by P3) imports that module or re-implements it. A second implementation risks divergence and false FAILs, and it adds to P3, who already owns all Solidity changes, deployment, and 10 Foundry tests despite the team's unknown Solidity ability.

**Remedy**

> State that the auditor imports the gate's rule module unchanged. Consider moving the auditor CLI to P1, who owns the gate and record formats.

### R3-20 — consistency

**Problem**

> The stolen-key paragraph says '위반 시도는 모두 Denied 이벤트로 체인에 남는다', and the contract section says '탈취 키의 시도까지 모든 멈춤이 체인에 남는다'. Yet the same section reverts unauthorized calls (Unauthorized). A stolen agent key calling refund or setVendor therefore leaves no Denied event, only a status-0 tx if one is included at all.

**Remedy**

> Scope both claims to rule violations by authorized callers, and state that unauthorized-function attempts revert and are not recorded as Denied. Alternatively, make Unauthorized a non-reverting Denied as well.
